# M15 长桥 SDK 实时运行层

## 目的

M15 的长桥模拟账户实时链路需要由长桥 SDK 的行情推送驱动：实时行情或成交推送 -> 五分钟 K 线完成 -> 实时信号 -> 快速风控 -> 长桥模拟订单请求。它不读取本地模拟账本，也不使用旧快速队列作为下单来源。

SDK 行情运行层的入口是 `scripts/run_m15_longbridge_sdk_runtime.py`，配置为 `config/examples/m15_longbridge_sdk_runtime.json`。它将最终 K 线写入现有 `m15_realtime_market_events.jsonl` 契约，因此路由、执行、看板与审计产物不需要改变字段协议。

## 运行边界

- 仅允许 `lb_papertrading` 模拟账户；实盘、真实资金、期权和融资保持关闭。
- 行情使用长桥 SDK 订阅；下单复用持久 SDK 交易客户端，不允许每笔订单启动 CLI 子进程。
- 历史订单、成交对账、盈亏统计与日报继续在慢路径执行，不能阻塞实时订单处理。
- 实时事件文件在热路径只追加写入；每分钟心跳压缩为最近 20,000 条。SDK 运行进程保留必要的日线和盘中 K 线上下文；重启时只从自身事件文件恢复当天、每标的最近 20 根 SDK 五分钟已完成 K 线，作为结构判断历史。路由器仍只把本轮新事件作为信号触发源，执行器直接接收本轮新信号，因此不会重放旧信号或旧订单。
- SDK 订单显式指定常规交易时段、日内有效和纸面账户边界；影子配置默认禁止订单派发，防止 OAuth 完成后意外启用模拟下单。
- `1` 秒是信号产生到发起模拟订单请求的优化目标，`5` 秒内仍可接受；超过后必须用当前行情重新确认，不能补交旧信号。
- 延迟主口径在真正发起 SDK 请求时计算，包含同一轮前序订单的串行排队时间；整批策略处理耗时和单笔 SDK 请求响应耗时另行展示。配置、关联配置和实时 Python 源码共同进入运行指纹，后台看护发现任一漂移都会替换旧进程，避免文件已经修复而常驻进程仍运行旧逻辑。
- SDK 运行层停止或配置切换时，只向主进程发出优雅停止请求；主进程会先停止行情子进程、关闭进程间队列，再退出。这样不会遗留旧行情订阅进程，也不会让后续重启出现重复订阅。单笔 SDK 下单异常只写入该笔执行流水，不能让整个行情和下单运行层退出；下一根新 K 线只会为已明确失败、且没有长桥订单号的退出请求生成带新编号的重试意图，不会重复发送已提交或待确认的卖单。
- 行情子进程在五分钟区间中途启动或重连时，必须丢弃启动所在的残缺区间，并在状态里显示 `partial_bar_suppressed_until`；只有下一根从区间起点完整聚合的五分钟 K 线才能进入策略路由。
- 止损和止盈继续使用限价单，但多头卖出限价按当前价下浮 `0.5%`、空头回补限价按当前价上浮 `0.5%` 形成可成交保护区间。限价只是最差可接受价，正常情况下仍按当时更优价格成交；已有同标的退出挂单时不会重复提交。
- SDK 原生挂单维护每 `15s` 检查一次：未成交买入超过 `900s` 会撤销；已归因退出单超过 `60s` 未成交时，按当前 SDK 行情重新提供可成交保护限价。维护只处理带精确信号备注的 M15 订单，人工、未归因和部分成交订单不自动改动；状态文件长期保留最近一次实际撤单/改单动作，后续“无需操作”检查不能覆盖该审计证据。
- 本机当前 SDK 行情 WebSocket 固定使用 `cn` 端点；全局 WebSocket 在当前网络下会超时。交易状态 WebSocket 不是下单前置条件，默认关闭；SDK 的账户查询和订单请求仍走持久 HTTP 客户端，订单终态继续由慢路径只读对账确认。

## 验收后清仓

`scripts/run_m15_sdk_validation_flatten.py` 只用于用户明确批准的单次 SDK 纸面验收收尾。它必须指定授权的纽约交易日并带 `--execute`，且只会在美股常规交易时段、账户明确为 `lb_papertrading` 时工作。脚本先停止 M15 新开仓和后台看护、取消未完成订单，再根据长桥实际持仓方向提交多头卖出或空头回补；撤单最多等待 `30` 秒确认，清仓订单最多等待 `75` 秒确认实际持仓和挂单均归零。方向、价格、可用数量、账户状态或成交确认任一项无法确认时，整批清仓停止，不会猜测、补单或把“已提交”冒充“已清仓”。它不使用 CLI 下单，不读取本地模拟账本，也不会重启交易运行层。只有确认清仓完成后，才写入下一交易日的正式测试基线标记与新 epoch 状态。

如果停机后的账户或报价连接短暂失败，脚本最多做三次只读重试；账户/持仓/订单仍无法确认时整批停止。只有报价读取失败时允许使用长桥持仓成本价生成更保守的保护限价，并记录 `quote_fallback_used`。任何停机后的失败都会把正式测试写为 `pending_flatten`：后续 M15 可以恢复常驻，但执行层只生成长桥实际持仓退出，不处理普通策略开仓；看板和值守必须显示“仅允许平仓”。待长桥确认持仓和挂单均归零后，epoch 才从 `pending_flatten` 变为 `active`。

## 启用前置条件

1. 已在项目虚拟环境安装 `requirements-runtime.txt` 中锁定的 SDK 版本；启动器会自动重启到项目 `.venv`，避免系统 Python 找不到 SDK。
2. 将 OAuth SDK `client_id` 写入 `~/.config/price-action-trader/longbridge_sdk_client_id`，并在浏览器完成该客户端的授权。
3. 先运行 `python scripts/run_m15_longbridge_sdk_runtime.py --check`。它必须显示 SDK 和 OAuth 前置条件可用。
4. 通过模拟客户端集成验证后，才能把实际 M15 守护器从 CLI K 线轮询切换到 SDK 常驻运行层。切换时必须停止旧行情采集器，禁止两个来源同时写入同一事件文件。

Windows 隐藏登录启动项只调用 `scripts/start_m15_trading_stack_after_boot.sh` 一次；该脚本直接使用项目 `.venv/bin/python`，幂等拉起 M12.47、M15 SDK 和后台看护。虚拟环境缺失时明确失败，不回退系统 Python，也不创建周期性弹窗轮询。

日线实时确认只对本轮实际收到完整五分钟 K 线的标的生效。当天早先的 SDK 五分钟数据仍用于累计日内开高低收，但报价静默或当前区间没有推送的标的不会拿旧价生成新的日线确认；系统跳过该标的并在运行状态中列出当前批次缺失代码，不伪造零成交 K 线。

SDK 报价推送的 `current_volume` 按长桥定义为相邻推送之间的增量。每次新建或重连订阅时，每个标的首个报价快照只用于建立价格，不把其中的 `current_volume` 算进五分钟成交量；从第二次推送开始累加，防止首个快照把当日累计成交量误塞进一根五分钟 K 线并虚增放量分数。

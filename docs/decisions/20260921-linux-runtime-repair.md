# 主项目Linux修补与当晚串行测试

用户要求将实际系统按Windows成功样例的已知差异修补，并优先保留WSL/Linux。本轮从最新主线d368a7e建立独立修复分支，集成已审官方候选ab21734；不把一次Windows休市首推当作平台根因证明。

## 原因与处理

| 差异/缺陷 | 已有证据 | 本次处理 |
|---|---|---|
| 默认启动指向已删除的`.venv` | 默认入口在旧环境清理后无法找到解释器 | 正式入口统一`.venv-m15/bin/python`，启动前核验来源 |
| 实际系统未接入官方同步候选 | 旧行情异步桥接、分批和自定义行情端点仍在旧主线；独立Windows样例无这些包装 | 合入官方同步QuoteContext、默认Config、147只一次Quote+Trade；删除退役行情桥接与分批配置 |
| Linux主项目4.5.0，Windows样例5.0.0 | 包版本和平台不同；二者旧样例均有成功/失败，不能直接归因 | Linux升级校验通过的官方5.0.0；不改原包 |
| SDK时间缺少时区，父进程拒收 | 官方SDK返回本机naive时间；实际父报价校验要求aware时间，修复前不更新 | SDK专用边界按本机时区转aware UTC，严格校验不放宽 |
| 诊断日志不能保存datetime/Decimal | 首个此类消息可触发JSON序列化异常 | 仅为审计副本转换格式，实际处理仍保留类型 |
| Python/操作系统不同 | Linux3.12.3，Windows3.14.3；官方提供Linux cp312 wheel | 优先WSL/Linux，保留受支持版本，不凭推测迁移Python或改系统网络 |

**因果边界：** 默认入口及回调后的时间/日志错误可以直接复现；它们不能解释独立官方Linux样例在订阅阶段零回调超时。同步/全量/版本统一消除了实现差异，但不是已证明解决订阅故障。9月8日开盘断流和后续订阅初始化超时也尚未证明同根因。

官方依据：[订阅接口](https://open.longbridge.com/docs/quote/subscribe/subscribe)、[5.0.0官方发布](https://pypi.org/project/longbridge/5.0.0/)、[官方时间绑定源码](https://raw.githubusercontent.com/longbridge/openapi/v5.0.0/python/src/time.rs)。147只一次提交符合官方接口容量，不按经验增设批次；SDK本机时间转换不通过给naive值直接贴UTC标签完成。

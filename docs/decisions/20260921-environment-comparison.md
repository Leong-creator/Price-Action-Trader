两次开始相隔约25小时41分钟，未控制当时网络和服务端状态。SDK发布版本相同，但原生构建与Python不同；不能要求跨系统二进制哈希相同，也不能仅凭版本相同认定运行行为一致。

由此可以判定：

- “147只必然超额”“必须分批”“账户完全不能访问行情”“只有修改版SDK才会失败”，均不足以解释现有结果。
- 旧异步桥接、分批、日线预取、项目队列和策略都不在case011失败路径中，因此不是所有失败必须具备的条件。它们在正式链路是否还有独立问题，尚未被这个样例验证。
- 最近失败位置在认证/档案成功之后、订阅调用完成之前；尚未进入策略。日志只证明SDK内部等待订阅完成超时，不证明服务端没有回包。
- Linux此前也成功过。Windows一次成功不能证明WSL、Python、代理、DNS或某个SDK平台包就是原因，更不能证明9月8日开盘断流已解决。

原始私有证据分别位于项目外 `20260919-official-current-release/case011-official-sync147-v5-default` 和 `20260920-isolated-windows/case012-official-sync147-windows`。公开脱敏结果见 [case011](20260919-official-route-result.md) 与 [case012](20260920-isolated-windows-result.md)。本轮复核源码哈希及运行结果时间，未重复实连。

## 3. 网络差异能证明到什么程度

北京时间9月21日00:37:59只读现场比较：Windows与当前Linux进程的 `HTTP_PROXY`、`HTTPS_PROXY` 值相同，均指向本机HTTP代理；Linux另有小写变量、SOCKS代理变量及排除列表。两侧当前没有长桥地域或URL覆盖变量。**不能称Windows完全没有代理。** 两个系统中的相同本机地址也不保证实际线路相同。

当前Linux处在WSL2内核下，有两条默认路由及私网DNS；Windows原生网络配置不同。未能核实工具Linux进程是否存在额外网络隔离，因此不把它笼统归因于WSL发行版或Codex。此次没有主动解析官方域名，也未修改代理、DNS或路由。

历史case011仅记录代理保持原状，case012记录了代理变量名称；缺少两次执行时的完整可比配置和目标IP。这些当前差别不是已证历史根因。同一个 `.cn` 域名也不保证同一个服务器地址或线路。

官方 [接入说明](https://open.longbridge.com/docs/getting-started) 支持默认地域选择；[SDK故障排查](https://github.com/longbridge/openapi/blob/v5.0.0/README.md#troubleshooting) 要求检查HTTPS/WSS网络与代理/防火墙。已核查版本的行情WSS连接不直接读取HTTP代理变量；失败样例已完成WSS认证和档案请求，因此“网络完全不通”不符合该次证据，但间歇网络或连接路径问题仍未排除。

## 4. 针对差异的下一步

1. **先证明已成功路径能持续工作。** 依现行计划，用保留的Windows官方环境在真实交易时段验证147只报价和逐笔连续接收，记录订阅完成、最后数据时间、缺口与退出。保持单连接和官方调用，不恢复交易，不把周末首推当作整场通过。
2. **需要定位平台差异时，做有控制的有限串行对照。** 另立一次明确实验，在相邻时段统一Python版本、SDK发布版本、样例、认证和股票池，记录每次进程的脱敏环境、实际目标地址及阶段时间；Windows/Linux串行，确认前一个进程退出。平台原生包和网络仍是组合变量，不能宣称一次对照已分离它们。若两边都成功，结论是间歇性尚未复现，不能挑选旧失败判定Linux有缺陷；若差异可复现，再只对已观察到的网络或构建差异设计下一项实验。此项尚未实施，不重开旧的无差别重试。
